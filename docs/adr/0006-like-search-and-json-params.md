# 检索用 LIKE 跨字段扫描，生成参数存 JSON 文本列

检索与schema两项开工前挂起的决策已在切片 3 落地，此处补记为决策依据。

全文检索我们决定用 `LIKE '%q%'` 跨字段扫描（记录的提示词、备注、参数 JSON、工作流路径，外加 EXISTS 子查询命中关联配方的名称与参数），而非 SQLite FTS5。备选方案 FTS5 需要虚拟表 + 写路径触发器同步，而默认 tokenizer 对中英混排的提示词分词效果差（要 trigram 索引，体积翻倍）；MVP 是单人单库、条目量在千级，全表扫的延迟远低于交互阈值，且 `LIKE` 让过滤条件（工具 / 媒体类型 / 有无配方 / 待补录 / 时间区间）能与全文命中自由组合成一条 SQL，无需先查 FTS 再二次过滤。代价是命中不走索引：数据量上万或需要相关性排序时，再引入 FTS5 并把现有过滤条件保持为 SQL 级。

生成参数（seed、steps、cfg、sampler、模型名及各自定义节点值）决定存单个 `params` JSON 文本列，而非每参数一列或键值表。因为参数集随工具与工作流而变——ComfyUI 的节点图有几百种组合，可灵/Runway 又是另一套字段——建列会让 schema 每接一个工具就迁移一次，键值表则丢掉类型与顺序、也让「一键复制全部参数」需要重新拼装。存 JSON blob 使参数表可直接渲染、可整份复制、可原样回灌给工具复现，全文命中靠 `LIKE` 扫这段 JSON 即可（与上一条决策咬合）。代价是无法按单个参数值做索引查询或聚合统计；出现「按模型统计使用率」这类需求时，再针对热字段建规范化索引表，`params` 仍作为权威存储。词汇见 `CONTEXT.md`。
